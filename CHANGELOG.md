# Changelog

All notable changes to this project will be documented in this file. This project follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Fireworks provider template (OpenAI-compatible, `https://api.fireworks.ai/inference/v1`), with a matching model catalogue entry, dummy app seed block, and `FIREWORKS_API_KEY` in `.env.example`
- `Conversation#user`, a polymorphic association recording the signed-in person who started the conversation, held separately from `owner`. Ownership answers "which records may this request see" and can be redirected at an organisation with an owner block; the user answers "who is doing the talking" and is always whoever was signed in. The two are the same record until an owner block sends ownership elsewhere, and both are nil for an anonymous visitor on a public assistant. Tools read it as `user` alongside `owner`, so a tool can answer questions about the person who asked rather than only about the tenant they asked from. The conversations index now names the user in preference to the owner
- Tools are now given per assistant rather than shared by all of them. Registering a tool in the initialiser makes it available to pick; each assistant is then given its own set on its edit screen, held in a new `layered_assistant_assistant_tools` join table by tool name (tools are classes, not records, so a name whose class is no longer registered is ignored rather than raising). `ToolRegistry.for` intersects the assistant's set with the registry, and the runner re-checks it before executing, so a model that asks for a tool its assistant was not given gets an error back rather than a result. The owner check is unchanged and still applies on top: a public assistant's conversations only ever see tools declaring `self.public = true`
- Assistant messages record the model that actually served the response in a new `resolved_model` column, shown alongside the requested model in the message footer when the two differ. This makes routing models such as OpenRouter's Auto Router (`openrouter/auto-beta`) usable without losing track of what answered

### Fixed

- Model pickers are now scoped to the signed-in owner. `Model.available` is unscoped, so the assistant form's default-model select and the model picker on every conversation and panel composer listed enabled models belonging to *any* owner's providers, exposing their names across tenants. Models carry no owner of their own, so a new `scoped_models` helper filters them through their provider's owner, and an assistant's `default_model_id` is now resolved through it on write - an out-of-scope id 404s, as an out-of-scope `persona_id` already did
- The composer's `model_id` is now scoped too. Both the full-page and panel message controllers passed the posted id straight to the new message, so a request naming another owner's model had its response generated through that owner's provider, on their API key. The id now resolves through `scoped_models` and an out-of-scope one 404s. The public composers were never affected - they take the model from the assistant, not from the request

### Changed

- **Breaking**: a tool declares whether a public assistant may offer it with `self.public = true`, replacing `requires_owner false`. The word now matches `public` on Assistant, and the default is unchanged - tools are private, and withheld from the ownerless conversations a public assistant has. It is an attribute rather than a `public true` DSL because `public` is Ruby's own method-visibility keyword: a class method of that name would shadow it, and a tool whose body used a bare `public` to reopen visibility would silently mark itself callable by anonymous visitors
- **Breaking**: an assistant with no tools selected now calls no tools. Previously every registered tool was offered to every assistant, so after upgrading you need to give each assistant its tools on its edit screen (or with `assistant.update!(tool_names: [ ... ])`) before it will call anything
- The personas, skills, providers, models and assistants CRUD screens are now generated by [`layered-resource-rails`](https://github.com/layered-ai-public/layered-resource-rails), a new runtime dependency, in place of their hand-written controllers and views. Each screen gains search, sortable column headers and a row actions menu. Routes, URL helpers and ownership behaviour are unchanged - every resource scopes reads and stamps the owner through the engine's existing `scoped`/`current_owner!` helpers, so out-of-scope ids still 404
- Two provider behaviours do not fit the managed form and stay local: creating a provider still seeds its models from the catalogue, through a controller that overrides `create` alone, and the new-provider template picker keeps an ejected `new` template (held at `layered/assistant/providers` rather than the gem's `layered/providers` prefix, since engine view paths are global and the shorter path would also answer a host app's own `layered_resources :providers`). The choice of whether to seed a provider's models is now a select rather than a radio pair
- Flash messages on the migrated screens now read "Skill created" rather than "Skill was successfully created", and a record's delete action has moved from the bottom of its edit form into the index row's actions menu
- The nested models screen names its provider in the breadcrumb trail (Providers / Anthropic) instead of linking to Providers alone
- An assistant's name on the index now links to its edit page rather than to its conversations, matching every other index; its conversation count still links to the conversations. Its skills are picked with a combobox rather than a list of checkboxes, and `public` is a checkbox rather than a switch
- Bump `layered-ui-rails` from `~> 0.22` to `~> 0.25`, picking up the combobox control (`l_ui_combobox` and `as: :combobox` form fields), the Devise account settings screen with the sidebar account menu, view ejection, and the `--l-ui-navigation-width` token. No engine views needed changes; the dummy app now permits `name` for `:account_update` so the new Settings screen can save it
- Updated `data/models.json` with the latest models for each provider, ordered by recency and popularity

### Breaking

- Removed `Layered::Assistant.scope` configuration block. Engine records are now scoped to the signed-in user via a polymorphic `owner` association on every owner-bearing model (`Assistant`, `Conversation`, `Provider`, `Persona`, `Skill`), with reads filtered through `Model.owned_by(current_owner)` in controllers; when there is no signed-in user, `owned_by(nil)` returns no records rather than exposing unowned ones, and create actions raise `Layered::Assistant::MissingOwnerError` rather than persisting an invisible unowned record. The owner defaults to `l_ui_current_user` and hosts that want a different ownership boundary (e.g. an organisation) - including those that previously customised the scope block - should configure a `Layered::Assistant.owner` block in the initialiser instead

## [0.6.0] - 2026-07-14

### Added

- RuboCop linting via `rubocop-rails-omakase`, with a `lint` job in CI

### Changed

- Bump `layered-ui-rails` from `~> 0.10` to `~> 0.22` and migrate engine views, JS, and the dummy app for the breaking changes across that range: new BEM class names (utility/container/radio renames, strict BEM with every modifier paired with its base class, `l-ui-table__action` on table action links, `l-ui-checkbox` on checkbox inputs), renamed classes (`l-ui-select-wrapper` → `l-ui-select-container`, `l-ui-label--checkbox` → `l-ui-checkbox-container__label`, removed `l-ui--mr-2`), and opt-in section heading dividers (`l-ui-heading--section` on the setup page). The dummy app now imports the UI stylesheet from the engine's `builds/tailwind` path and regenerates `layered_ui_overrides.css` from v0.22.0, replacing the generator-copied local stylesheet; CI builds Tailwind before running tests
- Streaming render is now block-atomic: only fully-closed top-level markdown blocks are rendered, with a typing indicator standing in for the in-progress block. Each closed block fades in once when it arrives, replacing the previous per-token reconciliation

## [0.1.0] - 2026-03-14

Initial release.

### Added

- Multi-provider AI assistant engine for Rails 8+ with support for Anthropic, OpenAI, Mistral, and OpenAI-compatible local APIs (Ollama, LM Studio, etc.)
- Streaming responses via Turbo Streams with token fade-in animation and chunked markdown rendering
- Full conversation UI with composer, message history, and automatic conversation naming
- Configurable assistants with system prompts and default model selection
- Provider and model management with encrypted API secrets and provider templates
- Model sync service for fetching available models from providers
- Panel mode for embedding the assistant in the `layered-ui-rails` side panel via Turbo Frames
- Token usage tracking with estimates when provider totals are unavailable
- Guest conversation management
- Configurable authentication block with a `l_assistant_accessible?` view helper
- Install generator (`layered:assistant:install`) to copy CSS, register JS imports, and verify `layered-ui-rails` is present
- Migrations generator (`layered:assistant:migrations`) to copy engine migrations into the host app
- Polymorphic owner and subject associations for tying conversations to application records
- Kamal deployment support
- WCAG 2.2 Level AA accessibility
